包管理器是 JavaScript 项目里执行最频繁的命令，却往往是最少被认真选择的工具。2026 年的答案不再是"npm 还是 Yarn"：**pnpm** 已成为大量 Monorepo 的默认选择，而 **Bun** 内置的包管理器在速度上比它取代的工具快了一个数量级。

本文使用**可复现的真实基准测试数据**，结合最新版本号、GitHub Stars、npm 下载量和许可证条款进行对比。

## 详细分析

### 1. npm —— 稳如磐石的默认选项

npm 是参考实现：它随每个 Node.js 一同安装、拥有 npm registry，并定义了其他工具必须兼容的语义。12.x 延续了小步安全发布的路子 —— `npm ci` 更快、`overrides` 处理更好、workspace 支持更完善。

**典型场景：** 必须在纯净 Node 环境下零配置可用的项目、不希望引入额外工具的 CI、以及重视"稳定"胜过"极致速度"的团队。

#### 优点
- **零安装成本** —— 随 Node.js 分发，任何环境立刻可用
- **registry 的参考实现** —— 新 registry 特性总是第一个支持
- **行为最可预测** —— 所有 CI 镜像、Docker 基础镜像和教程都默认 npm
- **存在 `package-lock.json` 时 `npm ci` 快速且确定**
- **近期版本 workspace 支持已相当完善**
- **文档与 StackOverflow 答案最丰富**

#### 缺点
- **四个选项中实测最慢** —— 冷装 29.34 秒，热装 3.74 秒
- **扁平提升的 `node_modules`** —— 幽灵依赖会被悄悄装上
- **发布包体积最大** —— 2.93 MB（未压缩）
- **磁盘占用随项目数量线性增长**（无共享存储）
- **对 Node.js 版本要求较高** —— v12.2.2 需要 Node ≥22.22 或 ≥24.15
- **无内置运行时、测试器或打包器** —— 工具链需自行拼装

### 2. pnpm —— Monorepo 的事实标准

pnpm 将每个版本只存一份到全局内容寻址存储中，再通过符号链接把文件接入 `node_modules`。结果是：严格的依赖图（杜绝幽灵导入）、跨项目的大幅磁盘节省，以及安装速度约为 npm 冷装的 3.4 倍、热装的 2.2 倍。

12.x 版本还带来了 `side-effects-cache`、Monorepo catalog 支持以及更安全的默认配置。GitHub Stars（37.1K）已超过经典 Yarn —— 这是生态重心转移的有力信号。

**典型场景：** Monorepo、CI 密集的工作流、单机多项目的开发机，以及被幽灵依赖坑过的团队。

#### 优点
- **冷装速度仅次于 Bun** —— 实测 8.62 秒 vs npm 的 29.34 秒
- **下载量巨大** —— npm 周下载 3.278 亿 / 月下载 11.31 亿
- **业内最佳的 workspace 支持** —— `workspace:*` 协议、catalogs、递归脚本
- **默认严格模式** —— 隐藏依赖会明确报错而非静默安装
- **多项目下磁盘节省显著** —— 得益于全局存储
- **发布节奏活跃** —— 12.20.0 距 12.19.0 仅数天
- **迁移路径完善** —— `pnpm import` 可转换 npm/Yarn 锁文件

#### 缺点
- **符号链接的 `node_modules` 会破坏部分工具** —— 原生模块、打包器或旧版包偶尔中招
- **不随 Node 内置** —— Docker 和 CI 中需要额外安装步骤
- **实测字节数与 npm 相近**（7.5 MB vs 7.6 MB）—— 节省来自共享存储，而非单项目目录
- **严格模式可能带来意外** —— 依赖提升的存量项目迁移后会报错
- **全局存储增加了一个排查问题的概念**

### 3. Yarn（Berry，v4）—— 功能丰富的元老

Yarn 的现代化非常激进：Yarn 4 是单一小体积 bundle，默认使用 Plug'n'Play（PnP）—— 彻底取消 `node_modules`，并提供四个选项中最为深入的 workspace 能力。本次测试中我们使用 `nodeLinker: node-modules` 模式以进行同口径对比。

Yarn 的周下载量（1280 万）如今**不到 npm 的一半、pnpm 的 1/25**，如实反映了其 2017–2020 年巅峰之后的回落。技术依然优秀，但生态动能已经转移。

**典型场景：** 希望采用严格 PnP + zero-install 的 Monorepo、已深度使用 Yarn workspace 模型的团队、需要 `constraints` 做依赖校验的项目。

#### 优点
- **Plug'n'Play 彻底移除 `node_modules`** —— 解析更快，完全不存在幽灵依赖
- **Zero-Installs** —— 提交 `.yarn/cache` 后 CI 安装近乎瞬时
- **出色的 Monorepo 能力** —— `yarn constraints`、`yarn workspaces focus`、发布工作流
- **单文件 bundle** —— 1.27 MB，小于 npm 的 2.93 MB
- **锁文件确定性强、文档完善**
- **冷装 18.92 秒 / 热装 2.75 秒** —— 两个场景均明显快于 npm

#### 缺点
- **PnP 仍会破坏第三方工具** —— 很多项目需要覆盖 `nodeLinker`
- **生态下滑最明显** —— 8.1K Stars 为四者最低
- **npm 上的 `yarn` 是旧版** —— 直接安装得到 v1.22.22（Classic），Yarn 4 需要 corepack 或 `@yarnpkg/cli`
- **上手门槛更高** —— PnP、constraints、插件体系学习成本不小
- **所有实测场景均慢于 pnpm 和 Bun**

### 4. Bun —— 性能上的异类

Bun 把运行时、打包器、测试器和包管理器打包成一个二进制。其包管理器读取 `package.json`，从全局缓存通过硬链接安装 —— 在我们的基准中冷装仅 **4.09 秒**，是 npm 的 7.2 倍；热装 **0.07 秒**，几乎瞬时完成。

Bun 的 GitHub 仓库（9.67 万 Stars）是本对比中星数最高的，不过其中大多数关注的是运行时。2026 年末 Bun 加入 Anthropic，为这个本就活跃的项目增添了公司级背书。

**典型场景：** 愿意采用 Bun 运行时的全新项目、安装速度成为瓶颈的 CI 流水线、希望用一个二进制替代五个工具的开发者。

#### 优点
- **实测安装最快** —— 冷装 4.09 秒，热装 0.07 秒
- **可直接用于既有 Node 项目** —— `bun install` 兼容 `package.json` 并迁移锁文件
- **一个二进制，四件工具** —— 包管理器、运行时、测试器（`bun test`）、打包器
- **锁文件为可读文本**（`bun.lock`）
- **有公司背书** —— 现属 Anthropic
- **不依赖 Node.js** —— 独立运行，无引擎版本限制

#### 缺点
- **默认使用提升式 `node_modules`** —— 隔离严格性不如 pnpm 或 Yarn PnP
- **npm 包只是 0.01 MB 的包装包**，会下载平台二进制 —— 离线环境需要额外准备
- **想获得完整价值通常需要连运行时一起采用**
- **生态较年轻** —— 原生模块和 postinstall 脚本的边界情况仍会出现
- **Windows 支持成熟得较晚**

## 价格对比

四个包管理器**全部完全免费且开源**。没有付费档位、没有席位授权、也没有私有 registry 绑定。真正的成本是 CI 分钟数、磁盘和开发者时间。

|-------------|-----|------|------|-----|

| **CI 单次安装耗时（冷装，实测）** | 29.34 秒 | 8.62 秒 | 18.92 秒 | 4.09 秒 |

## 性能基准测试

### 安装速度 —— 实测可复现

基准项目：8 个直接依赖（`express@5.2.1`、`lodash@4.17.21`、`axios@1.7.9`、`zod@3.24.1`、`chalk@5.4.1`、`dotenv@16.4.7`、`dayjs@1.11.13`、`uuid@11.0.5`），安装完整传递依赖树（约 350 个包）。

| 场景 | npm 12.2.2 | pnpm 12.20.0 | Yarn 4.18.1 | Bun 1.4.4 |
|----------|-----------|--------------|-------------|-----------|
| **冷装**（空缓存、无锁文件） | 29.34s | 8.62s | 18.92s | **4.09s** |
| **热装**（有锁文件、删除 `node_modules`） | 3.74s | 1.70s | 2.75s | **0.07s** |
| **相对 npm 倍数（冷装）** | 1.0× | 3.4× | 1.6× | **7.2×** |
| **相对 npm 倍数（热装）** | 1.0× | 2.2× | 1.4× | **53×** |
| **`node_modules` 体积** | 7.6 MB | 7.5 MB | 7.5 MB | 7.5 MB |
| **`node_modules` 文件数** | 2,546 | 2,537 | 2,534 | 2,545 |

**测试方法：** Linux x64 容器、网络已预热，四者依次在同一台机器上运行。冷装 = 全新空包缓存、无锁文件；热装 = 缓存已由上一步填充、保留锁文件、计时前删除 `node_modules`。pnpm 与 Yarn 使用 `nodeLinker: node-modules` 以保证四者产出可比的磁盘目录。命令：`npm ci`、`pnpm install --frozen-lockfile`、`yarn install --immutable`、`bun install --frozen-lockfile`。

**结果解读：**
- Bun 的 0.07 秒热装主要由全局缓存的硬链接决定 —— 完全不触网。
- pnpm 的冷装优势来自存储 + 并行抓取，但热装仍需重建符号链接，成本高于 Bun 的硬链接。
- Yarn 若使用 PnP 模式会比这里的 `node-modules` 数据更快；我们主动选择了同口径模式。
- npm 冷装需要把完整依赖解压到扁平目录，29 秒是有代表性的数字，并非异常值。

## 什么时候选哪个

### 🎯 选择 npm 当：
- 你需要**零配置** —— 全新 Node 环境必须开箱可用
- 你的 CI 镜像和 Dockerfile 都基于 npm，不想折腾
- 你在维护**遗留项目**，有不想迁移的 `package-lock.json`
- 团队里有刚接触 Node 工具链的成员

### 🎯 选择 pnpm 当：
- 你运行 **Monorepo** —— 这是 pnpm 的主场
- 你被**幽灵依赖**坑过，需要严格隔离
- 你在**一台机器上维护多个项目**，在意磁盘占用
- 你想要**成熟稳定前提下的速度**，而不是尝鲜

### 🎯 选择 Yarn 当：
- 你想要 **Plug'n'Play**，真正实现零 `node_modules`
- 你需要在 workspace 间用 **`yarn constraints`** 做依赖校验
- 你已经有一个运行良好的 Yarn 4 Monorepo，迁移不划算
- 你希望用提交缓存实现 **zero-install** 的快速 CI

### 🎯 选择 Bun 当：
- **安装速度是你的 CI 瓶颈** —— 冷装快 7.2 倍，热装近乎瞬时
- 你在**全新项目**起步，愿意接受 Bun 运行时
- 你想用**一个二进制**替代 npm + jest + vite + ts-node
- 你能接受较年轻的生态以换取大幅性能收益

## 结论与选型建议

| 场景 | 最佳选择 | 理由 |
|----------|------------|-----|
| **Monorepo / workspaces** | **pnpm** 🏆 | Catalogs、`workspace:*`、严格树，且是"安全选项"中冷装最快的 |
| **追求极致 CI 速度** | **Bun** 🔥 | 冷装 4.09 秒、热装 0.07 秒，无人接近 |
| **零配置 / 遗留项目** | **npm** ✅ | 预装、可预测、无处不在 |
| **追求零 `node_modules`** | **Yarn 4** | PnP + zero-install，前提是工具链配合 |
| **单人维护多项目** | **pnpm** | 全局存储能省下真实磁盘空间 |
| **Docker / 生产镜像** | **pnpm** ✅ | 层更小，`--frozen-lockfile` 确定性强 |
| **全新项目、不限运行时** | **pnpm** | 速度、安全、成熟度的最佳平衡 |
| **全新项目、速度优先** | **Bun** 🔥 | 顶级安装速度 + 现代运行时 |
| **离线 / 内网环境** | **npm** 或 **pnpm** | Bun 的包装包需联网下载，除非预先缓存 |
| **团队已在用 Yarn 4** | **Yarn 4** | 运行良好的配置没必要折腾 |

**核心结论：** 2026 年已经没有唯一"默认答案"了。

- **pnpm** 是专业团队的最佳默认选择。冷装约快 npm 3.4 倍，免费获得严格的依赖隔离，并以 3.278 亿周下载量占据真实的行业使用量。今天要开一个 Monorepo，就用 pnpm。
- **Bun** 是性能天花板。4.09 秒冷装、0.07 秒热装不是渐进式改进，而是量级跃升。代价是更年轻的生态，以及实际上通常要连运行时一起采用。
- **npm** 依然是最兼容的选择，而兼容性本身就有真实价值。29.34 秒的冷装成本是用 CI 分钟数支付的，而不是用正确性支付的。
- **Yarn 4** 技术上一流，但已失去生态动能（8.1K Stars、1280 万周下载）。选它是为了 PnP 和 constraints，而不是为了趋势。

很多团队现在采用的务实方案是：**项目用 pnpm，速度关键的 CI 任务交给 Bun** —— 后者并不强制切换运行时。
